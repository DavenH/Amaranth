# Session Summary

Date: 2026-08-26

## Context

During the Cycle V2 source-layout migration, the initial proposal grouped
remaining runtime and UI code by function or lifecycle. The user clarified
that this would preserve the underlying discoverability and large-switchboard
problem exemplified by `EffectPreviewRenderer` and `ConcreteNodeEditors`.

## Decisions

- Organize concrete node behavior by domain first, not by generic function.
- Reverb, Delay, Equalizer, and other node domains should own their UI,
  preview, audio-processing, model, and editor implementations.
- Replace procedural dispatch such as `paintReverb`/`paintDelay` with
  domain-owned objects exposing operations such as `paint()`.
- Generic Runtime and UI modules may retain interfaces, orchestration, and
  registration, but not accumulate concrete node-kind behavior.

## Generalized Rules

- A tidier lifecycle folder does not solve a domain switchboard; follow concrete
  behavior to the domain that owns it.
- Prefer polymorphic or registered domain capabilities over repeated
  `NodeKind` branches in generic rendering, editing, preview, and processing
  files.
- Use file and object boundaries that make a domain implementation findable by
  its product name, such as `Nodes/Reverb`, rather than a broad category such
  as `Nodes/Effects`.
- When reorganizing, split mixed-domain translation units instead of moving
  them intact into a new generic directory.

## Open Questions

- The exact minimal capability interfaces and registration surface will be
  established by the active Cycle V2 source-layout TDD and existing node-module
  architecture.
